# Roblox pitfalls (field notes)

Each entry gives the symptom, the cause and the fix. Pair with `roblox-studio-ai-tools` for the current built-in Studio MCP tool list and `roblox-release-automation` for Open Cloud publishing.

## 1. Publishing

| Symptom | Cause | Fix |
|---|---|---|
| Open Cloud place publish returns 409 "Server is busy" | Field observation (not in the official docs): the place was open in Studio, which holds a collaborative edit session on it. The docs define 409 only as a conflict such as a place that is not part of the universe | First check that the place id belongs to the universe id. Otherwise close that Studio window, wait a few minutes, and retry. Keep a separate **dev place** for Studio work and never open the live place in Studio |
| Publish returns "Invalid Content stream" | Seen when we sent an XML `.rbxlx`. The docs say `.rbxlx` (`Content-Type: application/xml`) is supported, so also check the Content-Type and that the file is not truncated (another game published `.rbxlx` this way seven times without error, 2026-11) | Upload binary `.rbxl` with `Content-Type: application/octet-stream` (`rojo build -o x.rbxl`, or convert with Lune `@lune/roblox`) |
| The id in a Creator Hub URL publishes to the wrong thing | `/experiences/<id>` shows the **universe** id, not the place id | Resolve the root place from `cloud/v2/universes/<id>` first |

- Publish API facts: `POST /universes/v1/{universeId}/places/{placeId}/versions?versionType=Saved|Published` (Saved stores a version without releasing it; use it for staging). Scope `universe-places:write`. Body limit 10 MiB, 30 requests per minute. The API does **not** update EditableImage, EditableMesh, PartOperation, SurfaceAppearance or BaseWrap instances: publish places that rely on them from Studio.
- API keys: restrict by experience and set minimal scopes. IP allow-lists break keys used from Roblox servers; add an expiry only if you have a rotation process; a key unused for 60 days expires on its own. Keep keys in a secrets store or env file.
- Print one line such as "published version N" from the publish script, so the agent can quote it.
- Publish every playtest build to a private test place, and tell the tester 2-3 things to check plus the known issues.
- An agent never pastes API keys in chat. Keep them in a chmod 600 env file and read them inside the command only.

## 2. Loading Creator Store models

- `InsertService:LoadAsset` refuses models made by other creators. `AssetService:LoadAssetAsync` loads them in live servers only after the place enables **Allow Loading Third Party Assets**.
- In Studio, `LoadAssetAsync` fails. Pre-insert the models into a Studio-only cache folder in the dev place (insert with Studio MCP `insert_asset`), and let runtime code prefer the cache when it exists.
- Always keep a code-built primitive in the prop's place. Make it invisible only after the model is in, so a failed load leaves a usable box (collision and view blocking stay correct).
- **Ship audited pieces in the place; do not fetch them at each server start.** Cold `AssetService:CreateMeshPartAsync` loads of a 241-part store pack ran past a 15 s preload timeout in Studio, and pieces were missing on the first run (field note, 2026-11-08). Keep the audited MeshParts as templates in `ServerStorage` (in the place, or a Rojo `.rbxmx` model file so a rebuild keeps them, textured through `TextureID`, not a `SurfaceAppearance`: section 4) and clone them at build time. Rojo cannot write `MeshSize`, yet such templates rendered the same as a `CreateMeshPartAsync` copy in Play; loading them in a live server is unverified. Template MeshPart pieces only: `UnionOperation` pieces written into a template by Lune and resized at run time rendered several times too large (field note, 2026-11-08). A MeshPart written by Lune needs `InitialSize` set to the mesh's original size; without it the engine took the mesh size as 0 and Play drew the mesh far too big (field note, 2026-11-09).
- Sanitize every model: delete scripts, cap the part count, set decor to `CanCollide`, `CanTouch` and `CanQuery` false (except decor big enough for the camera to enter: section 4, 'The default camera'), and fit it to the primitive's box.
- Downloading with the Open Cloud asset-delivery API (field notes; the scope name `legacy-asset:manage` is not in the official scope list, so check the current docs): many **recent** Creator Store assets return 403 "User is not authorized" until the account "Gets" them into its inventory. Older ones download fine. Probe ids in a batch and filter. A Studio that fails every asset with the same words has lost its login, which is a different problem (section 3).
- Search: the documented endpoint is Open Cloud `toolbox-service/v2/assets:search` (beta, needs an API key with creator-store scope). The unauthenticated `toolbox-service/v1/marketplace/10?keyword=...&num=30` (10 = Models) and `/toolbox-service/v1/items/details?assetIds=` worked in our runs but are undocumented and may change. Studio MCP `search_asset` is the supported way inside Studio.

## 3. Testing in Studio through MCP

- Studio's Output can show no server logs at all, not even `warn()`. Read logs through MCP `get_console_output`, or run one-line `execute_luau` probes that return facts (positions, attributes, states) instead of printing. `get_console_output` can come back empty too (field observation, 2026-11-04): at the start of a run, connect `LogService.MessageOut` to append into a `_G` table from an `execute_luau` call in the same context (Server or Client), and read that table in a later call. `LogService:GetLogHistory()` works from `execute_luau` (tested 2026-11-08): each entry has `message`, `messageType` and `timestamp`, so filter `Enum.MessageType.MessageError` and `MessageWarning`. Use it also when `get_console_output` comes back cut off (field note, 2026-11-08). It keeps 512 entries by default (docs).
- Several Studio windows may be open. Call `list_roblox_studios` first and pass your dev place's `studio_id` on every call (the built-in server requires it). Never act on another project's window (window rules: `roblox-game-pipeline` section 0, rule 8).
- Old tool names from the archived Rust server (`run_code`, `insert_model`, `run_script_in_play_mode`, `get_studio_mode`) do not exist in the built-in server. Use `execute_luau`, `search_asset` + `insert_asset`, `start_stop_play`, `get_studio_state`. For scenario testing the docs list a `subagent` type `playtest`, but the Studio build of 2026-11-02 exposed only `explore`, `screen_capture` and `unit_test`: `playtest` needs the Playtest Agent beta (File > Beta Features). Without it, drive the playtest with `start_stop_play` and the input tools.
- **Wrong window.** Every Studio window shares one MCP connection, and calls queue through it. A call without the right `studio_id`, or after the user switched windows, lands in another place (community reports, C). Re-check `list_roblox_studios` when a result names an unexpected place.
- **Studio ids do not last.** `list_roblox_studios` shows `name: null` until a place has finished opening, a relaunched Studio gets a new id, and a window can close between turns (`studio_id is not connected`). Re-list before each batch of calls (field observation, 2026-11-03). Since the 2026-11-04 update each place also gets a new id when a window switches places. A Studio opened right after another was killed with `kill -9` stayed stuck before its place opened (`name: null`, every call "Place is not open"); a plain `kill` of it and a relaunch with an absolute file path fixed it (2026-11-04). Use `kill -9` only on a window that ignores `kill`.
- **Studio lost its login.** "User is not authorized" or "Authentication required" on every asset, even public ones, means this Studio is signed out, not that those assets lack rights (unlike the Open Cloud 403 in section 2). Ask the user to quit Studio (Cmd+Q on macOS) and reopen it signed in (window rules: `roblox-game-pipeline` section 0, rule 8). Report the art as unverified until then (field observation).
  - An outage of about 75 minutes on one Mac (field note, 2026-11-09):
    - Every fetch failed with AssetDelivery 401 "Authentication required to access Asset", while the Studio log still said logged in.
    - Restarting the windows did not help; a full Log Out and Log In by the user did.
    - A window opened while signed out sits at the login dialog and never registers with Studio MCP. Close it and reopen it after the login.
    - Symptoms to recognize: Cube meshes fail with "Failed to load mesh asset", and `rbxassetid://` textures go blank.
    - Built-in `rbxasset://` textures kept rendering, so lighting and geometry could still be judged.
- **A new window stuck at the login screen.** A newly opened Studio can stop at the Roblox login screen and never show up in `list_roblox_studios`, while windows opened earlier stay connected (field note, 2026-11-08). Report `BLOCKED` and ask the user to sign in in that window; do not kill and relaunch it in a loop.
- Data store or MemoryStore calls from `execute_luau` fail even in a test place until MCP Permissions has Save & load data on (`502 ... Access forbidden` when off) and the game has Security > Enable Studio Access to API Services (403 "API access is not enabled" when off). A local `.rbxl` cannot hold MCP permissions ("Save to Roblox to manage MCP permissions"), so use a place saved to Roblox. An `open_cloud_invoke` call refused with the permission already on hit an endpoint that accepts API keys only: use a Studio tool, an API key or Creator Dashboard (`roblox-studio-ai-tools` section 1a).
- A Server `execute_luau` call that waits for tens of seconds fails with "Target is not reachable". Start the work in one call (set an attribute, `task.spawn`) and read the result in a second call.
- "Edit datamodel is not available in Play mode" and "Start play hasn't finished yet" mean an Edit-context call overlapped a Play start or stop (field observation). Send Studio calls one at a time, in the order given under 'Edit and Play do not overlap' in `roblox-studio-ai-tools` section 2.
- "The current thread cannot reparent 'Script' ... additional value for the Capabilities property: Network" or "lacking capability Network" from `execute_luau`: since the 2026-11-04 update the call runs without the `Network` capability unless MCP Permissions > Connect to the internet is on, and a local `.rbxl` cannot have it (tested 2026-11-05). Create scripts with `multi_edit` or Rojo instead of parenting them from `execute_luau`; for HTTP, `require` or data stores use a place saved to Roblox with the permission on (`roblox-studio-ai-tools` section 1a).
- Long Luau kept on disk (needs the `Network` capability, so not on a local `.rbxl`; there, paste the source into `execute_luau` or create the script with `multi_edit`): serve its folder in the background (`python3 -I -m http.server <port> --bind 127.0.0.1`, started with run_in_background and stopped by PID afterwards; never in the foreground, `roblox-dev-workflow` section 8), then in one `execute_luau` call turn `HttpService.HttpEnabled` on (from an MCP client since the 2026-11-04 update, also MCP Permissions > Connect to the internet with `127.0.0.1` in the HTTP allowlist, or the call fails with "not in the Assistant HTTP allowlist"), `GetAsync` the file, put the source in a ModuleScript under ServerStorage, `require` it, destroy the module and restore `HttpEnabled` (tested 2026-11-03).
- `multi_edit` matches the old text exactly, whitespace and tabs included; a failed match means re-read with `script_read` and copy the text, not retype it. `script_grep` and `script_search` can return stale results right after an edit (community reports, C): confirm with `script_read`.
- Duplicate tools: the official Roblox Studio plugin and a manual `Roblox_Studio` entry both connect, so every tool appears twice. Keep one (`roblox-studio-ai-tools` section 1).
- Lune unit tests with mocks miss engine ordering bugs. Example: `CharacterAdded` can fire **before** the character is parented to `workspace`, so code that needs `char.Parent` silently skips. Back pure-logic tests with in-engine **bot scenarios**:
  - server-side bots run a scripted case (walk into the guard's view, freeze, carry an object together);
  - the scenario returns PASS or FAIL lines that the agent reads through MCP.
- A Studio attribute override per feature (skip intro, force a guard type, force a server mode) keeps scenarios deterministic. Every override is a no-op unless it is set. For random results, a Studio-only force (next roll = item or tier N) lets every tier's reveal be captured on demand (`roblox-fun-effects` section 12).
- A scenario that fails on the base commit too is pre-existing. Prove that in a throwaway worktree before you blame your change.
- **Screenshots** (`screen_capture`) work from a background Studio window on the current macOS Space (10 of 10 captures from a guarded background window, 2026-11-04) and time out when the window sits on another Space. Never bring Studio to the front for a shot: activating it takes the user's keyboard and mouse. Since the 2026-11-04 update a playtest started from an MCP client no longer brings Studio to the front. Open it in the background and keep it there (`roblox-studio-ai-tools` section 5). Studio throttles hard (15 fps and below) when it is not the frontmost app, so FPS read from it is not a measurement: ask the user for an FPS reading or measure on a device. Timings too: the same build code measured 70-133 ms over 5 runs in one background window (field note, 2026-11-08), so compare a change only against a baseline run several times in the same session. A shot still running after 120 s did not come back: stop it and take it again.
- **Phone framing from a desktop capture.** `screen_capture` returns the window's viewport. `Camera.FieldOfView` is vertical (docs), so a phone at the same camera sees the same height of world and a width set by its aspect: a full-height centre crop to the phone's aspect shows the phone's world view (field note, 2026-11-09). This works only when the window is wider than the phone. A landscape phone (about 2.2:1) is wider than a 16:9 window, so widen the window first, or the sides are missing. The HUD in the crop stays desktop-scaled; check UI at device sizes instead (`roblox-ui-layout` section 6).
- **Fast moments.** `screen_capture` returns seconds after the call, so a 0.4 s crack or a burst peak is gone by then (field observation, 2026-11-04). Freeze the effect first (`ParticleEmitter.TimeScale` 0 and a longer `Trail.Lifetime`, test only), or add Studio-only hold points to the flow: at each named beat, when `RunService:IsStudio()` is true and a player attribute (for example `FlowHold`) names that beat, the flow sets `FlowHeld` and waits until `FlowHold` is cleared. The agent sets `FlowHold`, waits for `FlowHeld`, captures, then clears it. A loading screen that closes in under a second: in Play, from a Client `execute_luau` call, clone its `ReplicatedFirst` LocalScript into `PlayerGui` so it runs again, wait until its ScreenGui exists (about 0.6 s), then clone that ScreenGui under another name and set the bar by hand; the copy survives the script's fade and `Destroy()`. It shows the look, not the load time (field observation, 2026-11-04).
- **Meshes not loaded yet.** Meshes a session had not loaded before stayed invisible for more than 3 s on their first view, in Studio Play, in `screen_capture` shots and by eye (field note, 2026-11-08). Show or build the area once and wait before the shot, and judge a missing mesh only on a second view. `ContentProvider:PreloadAsync` on the templates is untested for this. Lighting lags too: frames right after `LoadCharacter` rendered very dark, local lights missing, for several seconds in a background window; a 15 s settle gave the real look (field note, 2026-11-08). Wait about 15 s, or shoot twice, before judging lighting.
- **`settings().Rendering.QualityLevel` is the user's own Studio setting.** Setting it from `execute_luau` to measure a quality level changed the user's Studio render setting (field note, 2026-11-09). Read it first and restore it (usually `Automatic`) after measuring.
- **`execute_luau` is not a game script.** It runs with plugin capability, so a write that works there can still fail in a real script (field observation; the docs do not name its level). `SurfaceAppearance` map writes (docs: `PluginSecurity`, section 4) are an example. `CollisionFidelity` is a separate case (docs: scripts cannot read or change it at runtime): set it in Edit mode or in the asset, or pass `CollisionFidelity` in the `options` table of `AssetService:CreateMeshPartAsync` (docs). Re-test every property write from a real Script in Play.
- Members the docs tag `RobloxScriptSecurity` should be out of reach of `execute_luau` too (inference from the plugin-level observation above; field observation: reading `Lighting.Technology` failed, writes untested): `Lighting.Technology` is tagged read and write `RobloxScriptSecurity` (docs: only modifiable in Studio; deprecated in favour of `LightingStyle` and `PrioritizeLightingQuality`, which scripts can set). `MaterialVariant` maps (docs: `PluginSecurity`) failed to author from `execute_luau` in one run (field observation; cause unconfirmed, so probe with `pcall`). Put such values in the Rojo project (`*.model.json` under `MaterialService`) so `rojo build` ships them, and set them by hand in the dev place.
- `execute_luau` resets `Camera.CameraType` from Scriptable to Custom when the call returns (Output: "The execute_luau changed camera type"). A cutscene then shows the default camera in every screenshot. Re-arm it inside the call with `task.delay(0.2, function() camera.CameraType = Enum.CameraType.Scriptable end)` and capture right after. For a camera that must persist across calls in Play, use the render-step binding in 'Screenshots in Play' below.
- **Screenshots in Play.** `screen_capture` camera arguments do not stick in Play: the tool is an edit-time capture and the game's camera script overrides them (field observation). From a Client `execute_luau` call, bind one render step at priority `Enum.RenderPriority.Camera.Value + 1` (docs: lower numbers run first, the default camera runs at 200) that sets `CameraType` to Scriptable and the `CFrame` every frame; disable the ScreenGuis; capture with no camera arguments. Use one fixed binding name and `UnbindFromRenderStep` before re-binding and after the shots, or two loops fight. After the unbind the Custom camera kept the scripted CFrame: set `CameraSubject` back to the Humanoid and reset the CFrame (or respawn) before a join-view shot (field note, 2026-11-09). For top-down layout shots under a night haze, switch to a flat test light (`ClockTime` 12, grey ambients, `Atmosphere.Density` 0), saving the old values as attributes on `Lighting` first and restoring them after (field note, 2026-11-09). With `StreamingEnabled`, first call `Player:RequestStreamAroundAsync(position)` from the server for a far area (docs: temporary, not guaranteed), then capture right away. `AlwaysOnTop` GUIs do not show in captures (field observation; to see one, clone its holder into a temporary ScreenGui for the shot, which shows the look but not its world position, field note 2026-11-09); plain `BillboardGui` labels and floating numbers did show in Play captures (field note, 2026-11-09; Edit captures drew none: section 4, 'Non-Latin text'). Verify the missing ones by their properties (`Enabled`, `Adornee`, `Size`, `MaxDistance`, text) and by eye in a play session.
- **Client-built geometry does not exist on the server** (field observation; build side: `roblox-engine-2026` section 3). A server `PivotTo` of the character into such an area dropped it through the floor. To look at the area, aim the scripted camera at it (Screenshots in Play, above); do not move the character.
- A `require` from `execute_luau` gets a fresh copy of a ModuleScript, so module state (sessions, caches) is empty there. `game:IsLoaded()` is false in the Edit DataModel, so a module that waits on `game.Loaded` hangs when an Edit call requires it: the call timed out with no error, and the hung thread kept its clone parented (field note, 2026-11-09). Skip that wait when `RunService:IsRunning()` is false (judgment). Drive the running game through its own remotes or debug actions instead, for example a `BindableFunction` hook that the game's server script creates only when `RunService:IsStudio()` is true and a Server `execute_luau` call invokes. Set `OnInvoke` before the first `Invoke`: an `Invoke` yields until a callback exists and never resumes if none is ever set (docs), so an early call hangs the `execute_luau` call.
- **Animations built by script** (`KeyframeSequenceProvider:RegisterKeyframeSequence`) play in Studio and not in live servers (docs): upload them (`roblox-character-motion` section 6). To pose a rig in Edit mode for measuring or screenshots: load the track, `task.wait(0.3)` until `Length > 0`, set `TimePosition`, call `Animator:StepAnimations(0)`. `IKControl` is not evaluated that way; test IK in Play. A rig from `Players:CreateHumanoidModelFromDescriptionAsync` with a blank description is all black, so set body colors before screenshots (tested 2026-11-03).
- **Rest pose on a live character.** Idle and walk tracks tilt the limbs, and a screenshot of that looks like a broken body. Before a body check in Play: `Stop(0)` every track from `Animator:GetPlayingAnimationTracks()`, set the `Animate` script's `Enabled` false, set each joint's `Transform` (`AnimationConstraint`, or `Motor6D` on old rigs) to `CFrame.identity`, then re-arm the scripted camera (see 'Screenshots in Play').
- `user_mouse_input` moves do not fire `MouseEnter`, so hover tooltips never open. Toggle the tooltip's `Visible` in a probe to check its placement.
- **Input tools** (argument shapes: `roblox-studio-ai-tools` section 2; field observations). A capture is not in viewport pixels, so never click capture coordinates; use an `instance_path`. Give every clickable instance a unique name: an `instance_path` can resolve to a hidden button of the same name. A Scriptable camera can block `ProximityPrompt` E presses (docs: `RequiresLineOfSight` is tested from the camera). A prompt also shows, and E or `InputHoldBegin` fires, only while it is on screen: after a script moves the character, the Custom camera can stay behind facing away, so aim the camera at the prompt first. To click a world object, compute `Camera:WorldToScreenPoint` in a Client call after the camera has settled; points taken during a camera ease missed (field observations, 2026-11-04). Move the character with `Humanoid:MoveTo` from a Client `execute_luau` call, and judge each leg by the distance to its goal, not by `MoveToFinished`: one left over from an earlier `MoveTo` arrived late (deferred events) and ended the next leg early (field note, 2026-11-08). Gamepad KeyCodes (`ButtonY`, `ButtonB`) sent through `user_keyboard_input` did not fire Input Action System bindings that F and G fired (field note, 2026-11-09), so this route does not verify gamepad paths: review the bindings in code and test on a controller.
- Lune mock tests that run the whole client are slow, about 3-4 s of real time per simulated second; a long `Sched.advance(60)` looks hung, and parallel runs make it worse. Print a timestamp per section before calling it a hang. macOS has no `timeout` command.
- Lune and Studio each miss one MeshPart field (field notes, 2026-11-09). Lune could not read `MeshPart.MeshId` from store model files ("missing default value"); pulling the ids out of the file with `strings` worked. Studio Luau cannot read `InitialSize` ("not a valid member"; it is not in the API reference), so check that one in Lune.
- **Close what you opened.** Each Studio window holds about 0.3-1 GB (measured 2026-11-03), and five or more open windows have slowed or crashed the machine. When a task ends, stop play, save (Rojo or Script Sync files; Ctrl+S for Studio-only edits, which no MCP tool can do), then close the windows the agent opened by PID, never by pattern, and never another project's window. Full rule: `roblox-game-pipeline` section 0, rule 8.

## 4. Engine limits that bite

- **Teleports in Studio: `TeleportAsync` only, one experience.** Since 2026-11-05 `TeleportAsync` runs in Test and Team Test without publishing: the destination opens as a new test server, and MCP playtests, server inspection and the debugger carry over (DevForum). Limits from the post: the deprecated `Teleport`, `TeleportPartyAsync` and `TeleportToPlaceAsync` do not run; only places of the same experience; in local Test `game.PrivateServerId` and `game.JobId` are always empty, and in Team Test every server is private, so the reserved-server check below misreads in both; in Team Test `ReservedServerId` can differ from the destination's `PrivateServerId` (reuse the `ReservedServerId`); VIP teleports fail; `GetPlayerPlaceInstanceAsync` is unsupported. Untested by us (needs a place saved to Roblox with a second place). Keep one teleport module, and still verify the live hop on a published private build before release.
- One place can serve as both lobby and match. Detect a reserved server with `game.PrivateServerId ~= "" and game.PrivateServerOwnerId == 0`; a VIP server has an owner id. Treat teleport data as a client-visible hint and trust only who actually arrives.
- **DataStores:** use a separate store name in Studio (for example `PlayerData_Studio`) so Studio never writes live data. Never point a scratch place at the live game with `DataModel:SetPlaceId` and `DataModel:SetUniverseId` (the docs say both must be set to give an unpublished place `DataStoreService` access): ProfileStore then used the real DataStores (field observation). Use a test place or `store.Mock` (`roblox-data-saves`).
- **Light `Range` is clamped at 120 studs** (docs: `Lighting.ExtendLightRangeTo120` reference says the maximum `Range` of `PointLight`, `SpotLight` and `SurfaceLight` is always 120 studs). An earlier run of ours saw a cap near 60 (field observation), so measure on your build. A flashlight that must reach farther than the clamp needs a second light or a fake glow, not a bigger number.
- **Non-Latin text on SurfaceGui signs:** some fonts render Hangul broken in 3D (seen with GothamBold; the docs say Gotham fonts are removed and map to Montserrat, so the cause is probably Montserrat's glyph coverage). Use English sign text, or test a font that has the script before relying on it (Korean: Nanum Gothic, `roblox-ui-typography` section 7). Screen GUIs were fine. Not reproduced on 2026-11-03: Hangul rendered on a SurfaceGui and a BillboardGui in Montserrat, FredokaOne and Nanum Gothic during play. In that test, the MCP edit-mode `screen_capture` drew no SurfaceGui or BillboardGui text at all, so check world-space text in a play session.
- **Image ids:** a Decal id renders nothing in `ImageLabel.Image`; use the image (texture) id (`game:GetObjects("rbxassetid://<decalId>")[1].Texture` in `execute_luau`, or `asset.textureId` from the toolbox details endpoint). Probe it by setting it on an ImageLabel and calling `ContentProvider:PreloadAsync({label}, callback)`: only `Enum.AssetFetchStatus.Success` means it renders. `AssetService:CreateEditableImageAsync` probes only your own images. Docs: it loads only images owned by or shared with the experience owner or the Studio user. On public Creator Store images it says "no permission" even though they render (tested 2026-11-04). Pass instances to `PreloadAsync` (docs: "an array of instances"): bare id strings returned Failure for images that rendered on ImageLabels (field note, 2026-11-08). `ImageLabel.IsLoaded` turning true once the label is on screen is a second check.
- **The default camera passes through non-colliding parts.** In the default `PlayerModule` (Studio 0.746, `CameraModule/ZoomController/Popper.lua`), a part pushes the camera in only when its total transparency is under 0.25, and the raycast uses `RespectCanCollide = true`, so parts with `CanCollide` false never occlude, even with `CanQuery` true; `TrussPart`s never do. Decor with `CanCollide` false (stair treads over an invisible ramp) let the camera sit inside it, and the screen went black at the stair foot (field note, 2026-11-09). Turn `CanCollide` on for decor the camera can enter and walk the path again to confirm nothing changed; an invisible blocker does not help, because transparency 0.25 or more is skipped.
- **Spatial queries skip `CanQuery` false parts.** `GetPartsInPart`, `GetPartBoundsInBox` and raycasts never return them (docs; `CanQuery` only takes effect with `CanCollide` false), so decor set up by the section 2 rule is invisible to an overlap probe. Check decor overlaps by comparing bounding boxes (`GetBoundingBox`, or `CFrame` and `Size`) instead (field note, 2026-11-09).
- **Decals or Textures stacked on one face.** Two Textures on the same face of one part drew in a different order between Play sessions, which changed the look and the measured numbers (field note, 2026-11-08). The docs order decals on one face by `ZIndex` (higher draws on top), so give each layer its own value (untested by us); the fix that was tested puts the second layer on its own invisible part.
- **Mesh colour textures: upload at 1024.** A 2048 colour map (3.5 MB, approved) showed on an ImageLabel but stayed grey as `MeshPart.TextureID` in the client; the same art at 1024 rendered. 2048 roughness/metal maps were fine. `ContentProvider:PreloadAsync` reports Failure even for working ids, so test a texture on a MeshPart in a Play client instead. Flatten an RGBA texture (Cube's are) to opaque RGB before using it as `TextureID`: its alpha rendered black.
- **New uploads render blank for a while.** For 10-60 s after an upload the console shows `Asset content representation is being generated` and the part renders white, grey or garbled. Judge screenshots only after that message stops. The same warning also appeared in Play for 269 existing asset ids at once while everything rendered and no 401 followed (field note, 2026-11-09): when assets look right, it is not the cause of a problem, so do not chase it.
- **Mesh and map ids are not runtime-writable.** `SurfaceAppearance` `ColorMap`, `NormalMap`, `MetalnessMap` and `RoughnessMap` (and the write side of their `*Content` twins) need plugin security (a game script gets "lacking capability Plugin"), and no script can set `MeshPart.MeshId`; `MeshPart.TextureID` and `SurfaceAppearance.Color` are writable (creator-docs). Build the MeshParts and their SurfaceAppearance in Edit mode (`AssetService:CreateMeshPartAsync`), keep them in ReplicatedStorage and `Clone()` them onto live parts. These templates live only in the place file, so a Rojo rebuild drops them unless the project includes them (a `.rbxmx` model file whose `SurfaceAppearance` holds a `ColorMapContent` asset URI rendered, but Studio then uploads a texture pack for it in every session: see 'A `SurfaceAppearance` in a file-built place' below; field note 2026-11-08). `AssetService:CreateSurfaceAppearanceAsync` is no way around this yet: asset ids and DataModel Content need the Studio Beta "Mixed Content for CreateSurfaceAppearanceAsync" (File > Beta Features, 2026-11-05). With it off, an asset id fails for every map with "ColorMap value should be an EditableImage Content", although the docs example passes one for `MetalnessMap` (tested 2026-11-08 and 2026-11-09, Studio 0.746). Once live, an SA built at run time from asset ids is not stored in the place, so it may avoid the texture-pack uploads below (untested). For a mesh swap at runtime the docs list `CreateMeshPartAsync` without a security tag plus `MeshPart:ApplyMesh` (untested by us).
- **Neon does not glow on a textured MeshPart.** With a `TextureID`, `Neon` rendered like lit SmoothPlastic with the texture; only untextured Neon glowed (Studio Edit probe, field note, 2026-11-09). A glowing mesh needs flat Neon color (recipe in `roblox-feel-audio-vfx` section 3) or a `SurfaceAppearance` emissive mask, which brings the texture-pack uploads below.
- **`MeshPart.Color` does not tint a textured mesh.** With `TextureID` or `TextureContent` set, red, white and green parts showed the same texture colors, and the transparent texels of an asset texture rendered black (tested 2026-11-08, Studio 0.746). `SurfaceAppearance.Color` multiplies the color map: a white map turned green, and a red logo under green went near black. Under a `SurfaceAppearance`, the part's `Color` shows only through transparent color-map texels. Tint tiers and colorways with white areas in the color map plus `SurfaceAppearance.Color`, which game scripts can write (docs), in a place where the SA is baked once (next bullet); otherwise use one texture per tint through `TextureID`.
- **A `SurfaceAppearance` in a file-built place uploads on the signed-in account.** The engine bakes an SA's maps into one texture pack asset and keeps the reference in `TexturePackContent`, which only the engine can write (docs: "when the object is published"). A place made by `rojo build` or by a script carries the map Content but no baked pack, and each new build drops it again. Studio sessions that opened such places tried to upload a texture pack per SA without a publish, the first about 30 s after opening and before Play. With 379 SAs, one session logged about 700 `Failed to upload TexturePack (Reason: PublishService AssetUpload failed ... HTTP StatusCode: 429)` lines and "Rate limit exceeded for TexturePack uploads"; smaller builds logged timeouts (Studio logs, field note 2026-11-08). Studio logs no line for a successful upload, so a quiet log does not mean nothing went up. That breaks any no-upload rule (`roblox-dev-workflow` section 8):
  - Dev builds texture meshes with `MeshPart.TextureID` and no SA (the SA memory saving in `roblox-character-design` section 7 costs these uploads).
  - Mount SA templates only in a release project: open it once, let the packs bake, save, and publish from Studio, each step with the user's yes. Open Cloud publishing skips places with SAs anyway (`roblox-release-automation` section 1).
  - Store models that a script inserted and saved to `.rbxmx` (Lune) lose their baked pack too (field note, 2026-11-08); convert their SAs to `TextureID`.
  - After any SA change, search the Studio log for `TexturePack|AssetUpload|Failed to upload` (`~/Library/Logs/Roblox/` on macOS, or `LogService:GetLogHistory()`, section 3). Do not search for `PublishService`: it matches the harmless `StudioPublishServiceDependencies] setComponents` lines in every session.
- **There is no Studs material.** `Enum.Material` has no stud entry (checked against the enum reference, 2026-11-03). Studs are a surface type: use `Plastic` and set the faces you want (for example `TopSurface`) to `Enum.SurfaceType.Studs`. Recipes and what renders: `roblox-game-pipeline` `assets/part-looks/README.md`.
- **Body swaps on R15.** `BodyColors` overwrites `Head.Color`: set `BodyColors.HeadColor3`. On an `AnimationConstraint` rig, `C0`, `C1`, `Part0` and `Part1` are read-only aliases of the two attachments (docs): a one-time swap to parts of new sizes moves the rig attachments instead (field observation; the docs say not to modify `RigAttachment.CFrame` directly because it disrupts retargeting and costs performance, so re-test retargeting after the swap and never do it per frame); per-frame motion goes in `Transform`. Set the Humanoid scale values to 1 so the engine does not rescale the new parts.
- **Anchored roots ignore `Humanoid:MoveTo`.** An NPC posed by anchoring its root (sitting, cutscene) silently stays put when an AI later tells it to walk. Release the pose (unanchor, stop the clip) in one helper that every move path calls.
- **GUI draw order with `ZIndexBehavior.Sibling`:** a child's ZIndex only sorts among its siblings. A tooltip at ZIndex 60 inside a button still draws under a menu frame that is a later sibling of that button. Raise the button's own ZIndex (or move the tooltip to a top-level layer).
- **Big characters tip over.** Scaled or custom humanoids sometimes enter `FallingDown`/`Ragdoll` and lie on the floor. Call `Humanoid:SetStateEnabled` false for both on the client that owns the character (each client owns its own).
- **Players climb onto NPCs.** Walking into a collidable enemy model lets the character step up onto it. Put enemy parts in their own collision group and `workspace:RegisterCollisionGroup` + `workspace:CollisionGroupSetCollidable(enemies, characters, false)` (`PhysicsService` is deprecated and only forwards); hit detection by distance or query still works.
- **Terrain heights snap.** `FillCylinder`/`FillBall` plus an Air carve leave the surface at `4*floor(y/4) + 2`, and Air fills clear every cell they touch. For an exact floor height, write the cell layer with `WriteVoxels` occupancy, then check it with a raycast through MCP. Lune voxel mocks usually miss this.

## 5. Generating meshes with Roblox Cube (Studio MCP)

Related generators: `generate_procedural_model` builds parameterised objects from primitive parts (50 per rolling 24 h; poll with `wait_job_finished`), better than a mesh for shelves, fences, stairs or anything that must scale; `generate_material` returns a `MaterialVariant` for restyling parts. Roblox's own generators aim at All Ages content, so weapon and horror prompts may be softened or fail.

Studio MCP `generate_mesh` (Roblox Cube, `GenerationService`) makes a textured mesh from text. In our runs the result was published to the generating account's inventory with an asset id; the official docs describe the in-experience API (`GenerateModelAsync` returns a Model) and do not document that inventory step, so verify it on your build.

| What | Rule |
|---|---|
| Prompt | One object, shape first: "long low waist-high chest freezer with glass sliding lids". A list of sub-items ("counter with belt, register, card reader") gives only one of them. No scene words ("furniture store display"). A known name beats the shape words: with "ankylosaurus" in the prompt Cube drew a ceratopsian frill and horns in 5 of 5 tries, and "baryonyx" gave a bulky rex body in 3 of 3; describing the shape without the name fixed both at once. Similes are taken literally: "built like a giant armoured elephant" gave an elephant with trunk and tusks, "flat wide armoured tank" grew a gun stub, "like a giant armadillo" a domed shell, while "like a gharial crocodile" gave the wanted snout (one try each). Compare to an animal only when you want its parts, never to a machine. Face mood words ("menacing", "narrow eyes") were ignored in most of 65 jobs; pose, palette and jaw words did more (field notes, 2026-11-08 and 2026-11-09) |
| Size | A hint only. The long axis often comes out along Z: rotate the long side to your prop axis, `ScaleTo` the long side, put the base on the floor. Uniform scale keeps the AI proportions; set `MeshPart.Size` non-uniformly when the footprint must match |
| Triangles | Default 10,000. Lower budgets turn props blocky; use 8,000-10,000 for anything seen up close |
| Parts | `segmentation`: omitted means auto (Cube picks the parts), `"none"` gives one mesh for static props, `"explicit"` with `partNames` (max 8) gives one MeshPart per name. Ask for explicit parts from the start when a piece must move, such as wardrobe doors. Pass `partNames` as a comma-separated string (`"base, head, barrel"`): a JSON array inside the string came back with mangled names in one run (2026-11-08), although the schema accepts both. `segment_mesh` splits an existing mesh into at most 5 named parts |
| Variants | Generate 2 per object and pick one. Vague shapes ("island", "bunker", "box" freezer) come back as blobs |
| Rate | 1-2 jobs at a time is safe; 3-4 `async` jobs at once worked, and eight at once failed on publish with "Too Many Requests" (field observation). The limit is shared: three parallel lanes each running jobs hit "Too Many Requests" (2026-11-08), so keep at most 2 jobs at a time across all lanes on one machine |
| Mode | Runs in Edit mode only, not during a playtest |
| Uploads | In one game's 17 jobs the result was a Model with `SurfaceAppearance`s, while a bench in another test came with a plain texture and no SA (field notes, 2026-11-09); count SAs in each result. Studio uploads SAs it has not baked on the signed-in account (section 4); whether Cube's come baked is unverified. Every job also creates published asset ids for the mesh and texture. Read the mesh and texture ids, `Destroy()` the model in Edit right away, never park it in `ServerStorage` or save a place with it, and count SAs and search the log for `TexturePack`, `PublishService` and `AssetUpload` after the first job and every 5th: 0 upload lines in 17 jobs this way (field note, 2026-11-09) |
| Errors | "Failed to fetch image", "no generated model available" and MeshGen outages are transient: retry later with a shorter prompt |
| Moderation | Horror words ("sharp teeth", "wet skin") fail, and so did body words (thin, slim, skinny, flat chest, shirtless, gigantic). "bodybuilder" and "very muscular" passed. Describe shapes in mild words and retry near wording that already passed |

- Good for static props, furniture, vehicles and simple weapons (pistol, bat, pipe, forklift, lantern). It missed a crowbar twice, so check every weapon against a reference.
- Not for creatures that bend: the result is static with no rig, and `auto_setup_avatar` only rigs R15 humanoids. Explicit segmentation gives rigid parts you can joint by script, which suits turrets, robots and mechs; a raptor came back as 7 parts on the first try but with rigid legs and no knees (2026-11-08). Quadrupeds, spiders and other walking monsters need a Blender rig (`roblox-blender-export`). Designing the roster: `roblox-character-design`.
- A place used for Cube batches grows with every mesh: one reached 3.2 GB of Studio memory after about 30 robots (2026-11-08). Generate in a scratch place, keep a manifest of the asset ids (the results are in the inventory, above) so `insert_asset` can rebuild the models, and restart that window past about 2 GB.
- Stylized humanoid bodies work: one call for a headless body with arms down beat a hand-sculpted body. A "slim" or "skinny" prompt returned a toy-like figure with a block head, so generate a mid-size body and narrow it by scaling (field observation, 2026-11-03). Getting the mesh into Blender and cutting it into R15 parts: `roblox-blender-export` section 12.
- `generate_avatar` and `auto_setup_avatar` appeared in our MCP tool list but are not in the current official tool table (`studio/mcp.md`): list the server's tools before relying on them. `generate_avatar` returned a rigged R15 with a realistic human look, not the blocky Roblox style. The MCP call can time out on the client while the model still lands in `workspace` minutes later, so check the tree before you retry.
- Cube assets live in the generating account's inventory. Before publishing, check that the live place can load every one of them (a group-owned place may not).

## Studio-tested API notes (2026-11-01, Studio 0.745, scratch place via Studio MCP)

- `TextChatService.PlatformIntegratedChat` cannot be read from `execute_luau` (property read errors): set it in the Properties panel and playtest by hand.
- `BasePart:BindToCollisionSummaries` works from a Server `execute_luau` call during play: a part dropped from 30 studs reported the landing at relative speed about 108 with Normal (0,1,0) toward the part above the baseplate, then rebound contacts a few frames later. Use the dot product of `RelativeVelocity` and `Normal` for impact strength.
- `AssetService:PromptCreateAssetAsync` no longer exists; use `PromptCreatePlatformContentAsync`. Old tutorials and cached code that call it fail with a nil method.
- A beta API can exist as a class but not as a property: `UIShadow` and `AudioTextToSpeech` instantiate, `Camera.ProjectionType` (orthographic beta) does not until the Studio beta is on. Probe with `pcall(function() return obj.Prop end)` before scripting against a beta.
