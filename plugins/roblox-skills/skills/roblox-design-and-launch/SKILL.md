# Design, policy and launch

Read from the official creator-docs repository (state 2026-10-29). Numbers and policies change; the checks in section 8 say when to re-read the live page. Pair with `roblox-dev-workflow` and `roblox-store-art-pack` (icon and thumbnail craft).

## 1. Design

- **Core loop** = minute-to-minute interaction + most repeated action + progression engine. Write all three before building. A game without a progression engine feels shallow. Then check each core action against section 1b.
- **Prototype** with paper first (systems, UI flows, economy), then a greybox in Studio (feel, camera, controls). Paper gives speed and finds design flaws early, but cannot test feel and can give false positives; a greybox does.
- **Onboarding (first-time user experience):** teach the essentials, reach fun quickly, leave players wanting more. Measure the player funnel step by step and fix the biggest drop-off with an experiment. Player-facing instructions may be fewer than the funnel steps; keep the funnel step numbers and names unchanged so old and new data compare. Check that each step's reward covers what the next instruction asks for. Hide goal text after a short time (15 s in one game after a player complaint, 2026-11), keep the world guide (arrows), and show the text again when the step changes. Where there is no guide (a run, an arena), the text names the way out ("Press Exit, then ...") or players stall. A first pickup or reward placed straight ahead of the spawn, on the camera axis, is hidden behind the avatar at join; set it about 5 studs to the side (field note, 2026-11-09).
- **UI/UX:** prioritise information (what is the player doing right now?), keep visual language consistent, follow platform conventions. Use plain words: every menu and shop item gets a one-line help text that does not repeat its label, no jargon, plain labels ("Play alone" over "Single mode") (judgment). Design for phone first, then scale up. Test layouts with Experiments, toggle platform or seasonal UI with Configs.
- **Economy:** every currency needs sources, sinks and a pacing target. Every stat or currency the player sees also needs a written answer to "what raises it" and "what is it for"; with no answer, cut it or give it a use. After removing a feature, grep for the currencies or stats it left with no use. Simulate the economy in a spreadsheet or Lune script before shipping prices (rules below). Avoid power that only paying players can reach if the game is for younger audiences.
- **Economy sim rules** (field observations):
  - In a tiered economy (price grows per tier, each tier adds a gain), retune price growth and per-tier gain together in the sim: cutting only the price lets progress run away. Live price tests (section 5) still change one thing at a time.
  - Run one bot policy per way to play: the intended path plus every shortcut (for example repeating one action, standing idle, camping in one spot), and assert that each shortcut earns less than the intended path. The intended-path bot must buy every item on the path; a sim that skips an item hides gate failures. Add a policy whenever you add a shortcut.
  - Run the sim to the end state before adding content: a stall near the end shows only there.
  - A gain that grows with the stat it raises (gain = base + a percent of current power) compounds: in one prototype an idle bot reached the top tier in about 5 min. `base * sqrt(1 + power * k)` stretched that to about 30 min (field observation, 2026-11-04). Assert a time-to-top for the idle policy.
  - Run the bot once per way players buy power too (free, and each permanent income multiplier), and compare where each first fails as a histogram, not only medians. In one game the free bot first failed at waves 6-10 while the bot with a 2x currency pass first failed at 21-26 in 79% of seeds: paying players met no wall. A local bump in enemy health over waves 13-17 (x1.28, 1.64, 2.10, 1.64, 1.28, every other wave unchanged) moved the paid median first fail from 23 to 15 and the share failing before wave 20 from 21% to 78%, while the free median stayed at 7. A ramp over the whole range would have moved every later wave too (field note, 2026-11-13; bot runs, live effect not recorded).
  - Harness rules that each cost a re-run (field note, 2026-11-13): count a "stall" as N failures since the best stage last rose, not N in a row at one stage (progress that creeps, failing at 22, 23, 24, 23, never fired the old rule); run slow and fast bot variants (think speed x1.25 and x0.8) and require every target to pass for both; at 40 seeds the median's noise was about 0.3 min, so confirm a close miss with about 190 seeds before retuning; past 10 minutes per report run seeds in parallel worker processes, and print the full override string in every sweep log (a cut header hid a parameter).
  - Check the sim's fights against engine fights before setting boss or wall numbers. In one game the sim said a first boss needed about 1,500 damage; 20 Studio runs (phone preset, a bot that walks at the nearest enemy, damage set per run by a debug command) showed 300-400, and a version eased by the sim fell in 6.7 s and was dropped. Run several damage levels (150 to 900), record clears, seconds on the stage and lowest health, set the values from those runs and refit the sim. A debug damage value may not scale the rest of the run, so check what it leaves out (field note, 2026-11-15).
  - Random shop offers that ignore the wallet are mostly unusable: on one game's bot only 35% of cards in the first 30 minutes (10% later) had a working Buy. Re-rolling a card the cash cannot cover into types it can raised that to 61-70% over 40 seeds; to keep some near-affordable goals, re-roll a card priced past 3x the cash into types priced between the cash and 3x (56% of short cards then within 3x, against 7-9% before). Track opens with something affordable and shown cards that are affordable; 43% of late opens still had nothing in reach, so no roll rule fixes a pacing gap (field note, 2026-11-15; bot runs).
- **A boss as the wall.** Log the minute each stage is first reached and read the average gap per stage in first sessions: the largest gap is the wall. In one game the first boss was the largest single stop (16% of stage-1 starters), at minute 3.4, costing about 2.4 min, and the next stage another 2.4 min. That game's owner kept the boss as the wall and set the stage after each boss to the boss stage's normal-enemy strength, so breaking the wall shows progress at once; a sim then cleared that stage inside the boss run (gap 4-13 s) where it had needed 1-6 more minutes. Easing the boss alone moves the wait behind it; ease its neighbours together and test the boss in engine fights (field note, 2026-11-15; live effect mixed with other changes).
- **The first ten seconds.** Judge them on a phone preset with numbers: the pixel height of the first enemy, the share of sampled frames with the attack effect in view, the time to the first kill, the share of the screen the action fills. Hold the first scripted event (a first wave or spawn) until the client reports its loading screen closed, with a server backstop (12 s in one game). There a closer, slower, bigger opening wave, a framing camera and a 2.2x wider beam took the first enemy from about 32 px to 71-82 px, the beam in view from 28% to 54% of samples and the first kill from 3.9 s to 3.3 s; a separate battle-view change raised the battle's share of a phone screen from 5.1% to 11.6% (field note, 2026-11-14; Studio preset, no real phone).
- **Genre craft:** for chunky simulator/tycoon looks use `roblox-ui-genre-studs`; for other genres use the UI rules in `roblox-engine-2026`. Weapons and damage: `roblox-combat-tools`; rounds, lobbies and teams: `roblox-match-flow`. Judge the idea against the live market (trends, keywords, competitors) with `roblox-market-research`.
- **Quests, daily rewards, season pass:** start from Roblox's official feature packages (missions, season passes, bundles, engagement rewards; docs `resources/feature-packages`) before hand-rolling one. Badges mark milestones; their award counts later show how far players get.

**Solo-viable checklist (check at planning time):**
1. Can one player finish the core loop alone, in an empty server? If not, name the fallback: bots or NPC allies (`roblox-bots-npcs` section 5), a smaller mode, or a short wait with a bot fill.
2. Is the minimum players to start 1 for the main mode? If a match needs more, set a timeout that starts with bots.
3. Does progress come from solo actions, with group actions as a multiplier (bonus XP, shared base, co-op boss, trading)?
4. Is there a reason to bring a friend: friend bonus, invite prompt (`SocialService:PromptGameInvite`, docs `production/promotion/invite-prompts`), joining next to friends (official Spawn With Friends module, docs `resources/modules/spawn-with-friends`), shared plot, leaderboard among friends, free private server for the group (`private-servers`; under-13 players may be blocked from them by parental settings)? Friend features must also work with zero friends: since 2026-09-30 the friends-list APIs (`Players:GetFriendsAsync` and related) return empty by default for Australian users under 16 (O). Count friends for a bonus on the server: `Player:IsFriendsWithAsync` per pair in a `pcall` (docs: `IsFriendsWith` is deprecated), cached, re-checked on join and leave (field note, 2026-11-11); whether the under-16 change also empties it is untested, so never gate progress on friend count. New (staff post 2026-11-23, DevForum t/5002678; not in the engine reference on 2026-11-24, not tested by us): `Player:GetFriendsInServerAsync()` returns the `Player` objects of a player's friends in the same server, and `Player:GetFriendsInUniverseAsync()`, called on `LocalPlayer` only, returns friends online in any place of this game (`User`, `PlaceId` and the server's `JobId` as `GameId`, both strings). Friends who hide their online status or current game are left out, and they return nothing for Australian under-16 users who turned the access off. `pcall` both; an empty array is a normal result.
5. Does the join-friend path work for a server that is full, private or reserved (`TeleportOptions` ids)?
6. Is anything that needs a crowd (trading, shops of other players, PvP) labeled as optional so an empty server does not look dead?

**Max players guidance (J, from the table):** solo-first or heavy per-player world (tycoon, base-building, obby with checkpoints): 7-12 keeps the world lively and cheaper. Social hubs, roleplay, battle games: 16-30 and up when the map and `StreamingEnabled` can carry it. Under 7 only for a deliberate co-op or horror format. Justify values outside 7-30 (`roblox-launch-benchmarks` gate 9). Per-player plot games (tycoon, garden, base): set `MaxPlayers` to the plot count, and hand plots out from a waiting list, not only at join; in one prototype a player who joined while all plots were taken never got one, even after someone left (field observation, 2026-11-04).

Re-measure the M rows with the `roblox-launch-benchmarks` scripts before quoting them after a month; re-read the V sources for new reports. For today's charts, keyword competition, competitor teardowns and decay curves, run `roblox-market-research`.

## 1b. Design rules (judgment)

Checks for the planning interview and for reviews of a running game. They are adapted to Roblox from a game director's video series on game design (frontmatter sources, read through a fan summary): judgment, not measurements, except where a line says docs. The brief wins over any of them.

- **Risk and reward per action.** For each core action write one line: what the player risks and what it pays. Put the payoff where the risk is: a jump from the very edge goes farthest and falls most often; melee range is also the range at which you get hit; a raid on another base pays only if the loot gets home. An action with no risk becomes a chore. Pair each pleasure with its opposite: speed needs places that slow you down, flying needs a fall below.
- **Stress, then release.** Every loop needs a stress (an enemy, a gap, a price the wallet cannot reach yet, a timer) and a release (the clear, the purchase, the growth). In a tycoon or simulator the stress is the next price, so keep it in view (rewards, below).
- **Retry fast.** The time from a fail to control again decides whether the player tries again, more than the size of the penalty. `Players.RespawnTime` defaults to 5 s (docs); set it per mode, usually shorter for obbies and short rounds. Keep the death moment short and showy (one to a few seconds), never respawn a player into a spawn kill, and never let instant respawns make a hard part free.
- **No dead ends.** A player who fails at the same place again and again is about to quit. Log fails per stage or checkpoint (a custom event, section 3a) and plan the relief before launch: an easier route, a hint, a skip after a few fails, or difficulty that eases after losses. Offer it without shaming the player. If a skip is also sold, keep a free relief as well.
- **Difficulty under your own.** The builder knows every answer, so set the difficulty lower than feels right and test with a handicap (one thumb on a phone, half health). Shape it as peaks and plains, not one ramp: a boss, then an easy stretch where the new power shows, then a place to earn (the boss wall, section 1). Do not scale enemies with the player's power in open areas, or growth stops showing. Give two layers: a plain way through for new players and a harder one for experts (optional challenges, a faster route, a stake that raises enemy strength and payout together).
- **Units with a one-line trait.** Every pet, tower, weapon or class gets a trait you can say in one sentence, and its numbers push that trait to an extreme with a matching weakness. Averaging units toward the middle removes the reasons to choose. Nerf what the trait costs (cooldown, recovery, range, price), not the trait. Units may share one script and differ only in numbers when the numbers differ a lot. In unit games build counters (A beats B beats C) and balance them by cost, not by random misses. Judge balance from play data, not from how strong a unit sounds. Looks follow the trait: `roblox-character-design` section 4.
- **Rewards planned with the skeleton.** List what the player earns (numbers, unlocks, looks) right after the core loop, before content. Every number earned needs a sink the player chooses. Keep the next goal on screen ("120 XP to level 5", the next item the wallet nearly reaches). In PvP, reward with unlocks and looks, not stats. Praise good play on the spot (a cheer, a short burst) and give the loser something to enjoy too (`roblox-match-flow` section 2, Results).
- **Errands (quests, missions, dailies).** A good errand pays in line with the trip, gives small joys at short gaps on the way, lets the player pick a route (long and safe, or short and risky), ends at the goal (send the player back at once; the walk home is not fun) and gives a reason to care (a question, a rumour). Build on the feature packages (section 1, quests).
- **Shortcuts players find.** A trick that takes skill or luck (a hard route, a rare enemy worth a lot) is part of the fun: cap it in the economy sim instead of patching it out. Idle and repeat-one-action shortcuts still earn less than the intended path (section 1, economy sim rules).

**Rewarded video ads** (docs `production/promotion/rewarded-video-ads`, `rewarded-video-playbook`, `rewarded-video-optimization`, `production/experiments`, engine reference `AdService`, `ShowAdResult`, `AdAvailabilityResult`, `ProductPurchaseChannel`; all read 2026-11-20):

- **Eligibility (docs):** game public and unrestricted, with no free-form user creation, strong language, romance or social hangouts with private spaces (the last three added to the page on 2026-11-12); Maturity and Compliance or Content Rating Questionnaire reviewed and approved by Roblox; an average of 2,000+ unique visitors a month. Publisher 13+, in good standing, ID-verified, 2FA on; the immersive ads page applies the age, ID and 2FA rules to the group owner for group games (the rewarded video page does not say). Turn it on at Creator Hub > Monetization > Ads > Settings > Rewarded Video > Serving and pick the reward there. Only some players can see ads: `PlayerIneligible` means "might be under 13 or located in a blocked region". Resubmitting the questionnaire removes ads eligibility while it is under review.
- **Rules (docs):** the reward is a developer product of the same universe that would normally sell for Robux in your shop, never Robux; it is not randomized and must not inflate currency or unbalance the economy. The player starts the ad with a clear action (a button) that states the reward and what to do before it plays ("Watch the ad to earn 10 diamonds!"); never a progress gate; grant right after the ad; do not take over the screen or hide avatar motion; the ad must not harm the character (pause damage while it plays, or offer it only in safe places such as the lobby). Breaking a rule can cost ad payouts or the account. Ads no longer close by themselves when the video ends: the player presses close (staff reply 2026-09-24, DevForum t/4700202).
- **Code flow (reference):** `GetAdAvailabilityNowAsync` runs on the client only and `ShowRewardedVideoAdAsync` on the server only. The grant comes through `ProcessReceipt` with `receiptInfo.ProductPurchaseChannel == Enum.ProductPurchaseChannel.AdReward`; the returned `ShowAdResult` must not grant anything. The docs' own client sample reads the result even when the `pcall` failed; check `ok` first:

  ```lua
  -- Client: check when the offer becomes visible (shop opened, defeat screen shown), not at join
  local ok, res = pcall(AdService.GetAdAvailabilityNowAsync, AdService, Enum.AdFormat.RewardedVideo)
  adButton.Visible = ok and res.AdAvailabilityResult == Enum.AdAvailabilityResult.IsAvailable
  adButton.Activated:Connect(function()
  	adButton.Visible = false
  	AdRemote:FireServer()
  end)

  -- Server
  local showing = {}
  AdRemote.OnServerEvent:Connect(function(player)
  	if showing[player] then return end
  	showing[player] = true
  	local ok, result = pcall(function()
  		local reward = AdService:CreateAdRewardFromDevProductId(AD_PRODUCT_ID)
  		return AdService:ShowRewardedVideoAdAsync(player, reward, PLACEMENT_ID) -- placement id optional
  	end)
  	showing[player] = nil
  	AdRemote:FireClient(player, if ok then result else nil) -- UI only
  end)
  -- In the game's single ProcessReceipt: if receiptInfo.ProductId == AD_PRODUCT_ID, grant and return PurchaseGranted
  ```

  `ShowAdResult` values: `ShowCompleted` (watched to the end), `AdNotReady` (not loaded, fetch failed or expired; also returned when the client had no ad available), `AdAlreadyShowing`, `InternalError` (try again), `ShowInterrupted` (closed the ad or left: no reward), `InsufficientMemory` (not enough video memory). `AdAvailabilityResult`: `IsAvailable`, `NoFill` (no ad, or the frequency limit was hit), `InternalError`, and `DeviceIneligible`, `ExperienceIneligible`, `PlayerIneligible`, `PublisherIneligible` (hide the offer). Call the availability check as close to the offer as possible, and after an ad again only if you offer another one (fill rate and memory). Placements are created at Monetization > Ads > Placements and their id goes to `ShowRewardedVideoAdAsync` (the docs' Placements section writes `ShowRewardedVideoAsync`; the reference name is `ShowRewardedVideoAdAsync`). `AdService:RegisterAdOpportunityAsync(button, placementId?)` (client) registers the offer button, a `GuiButton` under a `ScreenGui` in `PlayerGui`, and counts each time it is visible and unblocked, so opt-in rate can be read per placement.
- **Money (docs):** earnings = EPM (Robux per 1,000 impressions) x impressions, and the first frame shown counts as an impression. A published EPM or rate for rewarded video and its payout date: not published (the payout on the 25th of the next month is documented for immersive ads only). Monetization > Ads > Eligibility has an earnings calculator (eligible users of the last 7 days x daily ad views per user x projected EPM).
- **Measurement (docs):** Monetization > Ads > Analytics, filter Rewarded Video: Earnings (Robux), the funnel Requested > Filled > Ad Opportunities > Impressions > Rewarded, Fill Rate, EPM, DUV (daily unique viewers), AEPDUV, eligible DAU, DUV/eDAU, Opt-In Rate and Frequency (ads per user per day); DUV, AEPDUV and eligible DAU arrive a day late. Experiments have a Rewarded Video Earnings metric set (DevForum t/4988305, 2026-11-12; section 3): total earnings per user (ads plus products, passes, private servers and paid access), impressions per user, opt-in rate (eligible players who watched at least one ad), frequency (impressions over unique viewers) and ad earnings per user; Roblox sets impressions per user and total earnings per user as the goals. Drive the tested value (reward size, cooldown) from a config read with `GetConfigForPlayerAsync`. The staff post's examples: a revive after a loss against 2x coins at round end, 50 against 100 coins, and ads for non-payers only. **Exclude your most likely purchasers from Rewarded Video Ads** (Ads > Settings) hides ads from likely spenders; the docs advise it only when the same reward can also be bought, not for an ad-only reward.
- **Roblox's placement guidance (playbooks, not our data):** offer at natural break points (after a defeat, at the end of a level, on wait screens), when the player is out of currency or stuck, and with daily rewards and events; show the reward before the player commits; avoid a "Watch Ad" button with no stated reward, a button three taps deep in the store, and the same offer whether or not the player needs it. Self-audit: the prompt shows within a couple of actions after its trigger; more than one reward type; a cap of at least 2-3 prompts per session (or a daily equivalent); consumable, repeatable rewards (boosts, currency, extra lives) rather than one-time durables; near the core loop. Health targets: opt-in rate 10-20%+, frequency 2-4+, impressions per DAU 0.5+. The playbook cites a Roblox survey (2026-02, n=423) in which 81% of users preferred gameplay-progression rewards, 48% cosmetic and 22% access unlocks. No per-genre benchmark is published.
- **Join with Reward (docs, added 2026-11-18):** closed beta, mobile only. ## 3. Analytics and live ops

- Creator Dashboard analytics: engagement, retention (D1/D7 and beyond), monetization, acquisition, performance, crashes, demographics; custom, funnel, journey and economy events (section 3a), custom dashboards and alerts.
- Configs: up to 1,000 active configs, 100 conditions; read with `ConfigService:GetConfigAsync`/`GetConfigForPlayerAsync`; publish takes 15-60 s. Experiments run 14-60 days, 2 variants plus control, metrics D1, D7, playtime, ARPU, ARPPU, payer conversion.
- Instrument before launch: the minimum event set in section 3a.
- **Experiment guard rails (O):** Early Harm Detection watches the first 24 h and flags critical harm at -10% playtime, -20% ARPU or -20% payer conversion; it needs 10,000 enrolled users. A sample-ratio-mismatch (SRM) banner means stop and restart. Under about 1,000 DAU an experiment rarely reaches significance, so ship clear wins and watch the dashboard instead. `GetConfigAsync` does not apply experiment variants; use `GetConfigForPlayerAsync`.
- **Experiment metric sets (O, 2026-11-12):** chosen when the experiment is created. Default; Rewarded Video Earnings (ad opt-in rate, frequency, impressions, ad earnings and total earnings per user next to the default metrics; Roblox sets impressions and total earnings per user as the goals; section 2 "Rewarded video ads"); Custom (the default metrics plus up to three of your own, built from custom, economy and funnel events; any of them can be the goal metric). A custom metric can only use events that already have data, and the metrics cannot be changed after the experiment starts: log the events first (section 3a) and do not change how the code sends them while it runs. Experiment numbers add up over the whole run and count each player once, Analytics pages are daily, so the two differ.
- **Reading a release** (field notes, 2026-11-13 and 2026-11-16, one game; method, not a Roblox rule):
  - Know the lag. In the Analytics API, daily Roblox metrics stopped about 2 days before today (a cohort's D1 arrived about 2 days after its next day), while hourly custom events ran about 2 h behind. Judge a release on hourly custom events and wait for D1 separately; a health read 100 min after a deploy (events flowing, no defeat spike, no new errors) is a direction check, not a result.
  - Before the read, write a table of "number | before | expected direction" (for example: first sessions that end after the first evolution, down; minute-10 survivors, up) and judge the result against it (judgment).
  - Compare the same hours of the day: sum hourly unique users over the same window on each day (for example 18:00-01:59 UTC) and compare ratios such as minute-5 survivors over minute-1 users. Test each ratio with a two-proportion z, z = (p2 - p1) / sqrt(p(1-p)(1/n1 + 1/n2)) with pooled p, and raise the bar for many tests: after 8 tests only p < 0.05/8 = 0.006 counts (one ratio passed at p < 0.001, another sat at the edge at 0.007).
  - A release of about 40 changes cannot be pinned on any one of them: name the two or three candidates, say the cause is unproven, and ship smaller releases when you need an answer.
- Creator Hub has benchmark sets (Similar experiences / Genre) and retention by acquisition source; benchmarks do not affect ranking. Do not compare play-through rate across 2026-10-12: a measurement change raised impressions and slightly lowered PTR (Roblox says RFY was unchanged).
- **Experiments** (A/B tests) and **Configs** (remote values) ship balance and UI changes safely. Open Cloud exposes both for automation (configs API is beta, experiments API experimental, so expect changes; configs publish is limited to 10 per minute).
- `RecommendationService` lets you build in-game recommendation carousels (register items, log one impression per item per session, log quality actions, fetch).
- Live ops plan: a content cadence, events (Experience Events), and a weekly review of retention, funnel and error reports. Write the **first 4 weeks** before launch: one repeatable drop type (weekly-to-monthly, built on existing systems), one timed event announced as an Experience Event, one limited item or restock; check it against the holiday calendar. Chart games update constantly: 35 of 37 with 20K+ players had updated within 7 days (M, 2026-11-03), and seasonal events with a pass can lift an evergreen game sharply (MM2 +146% Sep to Oct 2026, V).

## 3a. Event tracking (AnalyticsService)

Docs `production/analytics/event-types` and its economy, funnel, journey, custom-events and custom-fields pages, plus the `AnalyticsService` reference, read 2026-11-06. Each type unlocks its own Creator Hub page; all are free.

| Type | Call (server) | Answers |
|---|---|---|
| Economy | `LogEconomyEvent(player, Enum.AnalyticsEconomyFlowType.Source or .Sink, currency, amount, balanceAfter, transactionType, itemSku?, customFields?)` | Where each currency is earned and spent, average wallet |
| Funnel, one-time | `LogOnboardingFunnelStepEvent(player, step, stepName?, customFields?)` | Where new players drop off |
| Funnel, recurring | `LogFunnelStepEvent(player, funnelName, funnelSessionId, step, stepName?, customFields?)` | Where a repeatable flow (shop, upgrade) is abandoned |
| Journey | `LogJourneyEvent(player, journeyName, nodeName, journeySessionId?, customFields?)` | Which branch players take when steps can come in any order (onboarding choices, quests, several routes to checkout) |
| Custom | `LogCustomEvent(player, eventName, value?, customFields?)` | Anything else: button use, ability use, mission time |

**Rules:**
- Events arrive only from the server of a published game, never from the client or Studio. Test in a published test place and check the near real-time **View Events** list on the Economy, Funnel or Custom page; charts take about 24 h. Tracking errors show in the error report.
- Log after the action succeeded (the purchase went through, not the attempt). When the client reports a step through a remote, check it on the server before logging (`roblox-engine-2026` section 4).
- Economy: the amount is always positive (the dashboard shows sinks as negative), and the balance is the one after the transaction. Start with the default transaction types (`IAP`, `TimedReward`, `Onboarding`, `Shop`, `Gameplay`, `ContextualPurchase`, as `Enum.AnalyticsEconomyTransactionType.X.Name`).
- Funnels:
  - A step counts once per user; repeats are ignored but still use up the rate limit.
  - Logging a later step completes the skipped ones.
  - Filters and the date cohort come from the first step. To start at join, log step 1 in `PlayerAdded`.
  - A recurring funnel takes a new `funnelSessionId` (`HttpService:GenerateGUID()`) per attempt; only the 10 most recent ids per user and funnel are kept.
  - After changing steps, start the dashboard date range on the change day.
- Journeys: configure the journey first (Creator Hub > Analytics > Journeys, or a `JourneysConfig` Creator Config through Open Cloud with `universe:write`). Names must match the published config exactly. 2-10 stages of 1-10 nodes. Node names have no commas, quotes or line breaks and do not start with `__`.
- Funnel and journey progress expires after 180 days without events.
- Prefer custom fields to more names: one currency `XP` with the class in a field, one event `PlantSeed` with `Plant - Cabbage` in a field. Up to 3 fields, keyed `Enum.AnalyticsCustomFieldKeys.CustomField01.Name` to `03`, string values only.
- `LogProgressionEvent` and its Start, Complete and Fail variants show in no Roblox chart yet; use a funnel or a custom event for level progress. The `Fire*` methods are deprecated.
- `GetPlayerSegmentsAsync(player)` (server, may yield) returns coarse buckets for personalizing at runtime: payer status, new, active, lapsed or reactivated, days played in the last 7, acquisition source. With no data it returns `HasData = false` instead of throwing.

**Limits (docs):**

| Limit | Value |
|---|---|
| Requests | 120 + 20 x CCU per minute, all `AnalyticsService` calls together |
| Custom fields | 3; past 8,000 value combinations, values group as "Other" |
| Currencies | 5 on the economy page, 10 in the limits table (the docs disagree; plan for 5) |
| Transaction types, item SKUs | past 20 types or 100 SKUs, values group as "Other" |
| Funnels | 10, up to 100 steps each |
| Custom event names | 100 |

Limits reset daily, and an event's data rolls off 90 days after it was last received.

**Minimum set before launch (judgment):**
1. An onboarding funnel: join (in `PlayerAdded`), first core action, first reward, first upgrade, then each tutorial step.
2. Economy source and sink events for every currency, with the item SKU on purchases.
3. A shop funnel (open, view item, prompt, bought) or a shop journey when there are several routes.
4. Custom events for the core action and each HUD button, with the variant (map, item, class) in a custom field.
5. A session-end event with the furthest funnel step reached and the session length, and one milestone per session minute mark (1, 2, 3, 5, 8, 10, 15, 20, 30). In one game they showed where first sessions end (7 exit steps, n = 483 in a day, average session from 43 s to 46 min by exit depth) and the exit rate per minute (21% leave in minutes 1-2, 22% in 2-3, 16% in 3-5, 11% in 5-8, 7-8% a minute after 10). Players who left after the first loop reset came back 4-5 times as often as those who left earlier (56-64% against 11-13% of next-day sessions): a correlation, and the count includes same-day rejoins, so read the ratio, not the level (field note, 2026-11-13).

When most sessions end inside the first minute, log three client facts before guessing at ads, load time or devices: seconds from the loading screen's close to the first input and its kind (touch, mouse, key, gamepad, walk), what the first tap landed on (the target, a HUD button, the thumbstick area, empty world), and the session's last activity; add a bounce event for sessions under 60 s that says whether the loading screen closed and whether any input came. Send the client reports through remotes the server checks. In one game 82% of 1,000 new sessions ended within 60 s, 94% of those after an input, and 63% tapped within 2 s of loading, with loads under 3 s for 67% and no crashes: players acted at once and nothing answered, so the "ad misclicks" guess was wrong. Make the first input of any kind (tap, key, stick, a tap on passive HUD) do the first tutorial action, and keep the funnel step names unchanged so before and after compare (field note, 2026-11-16; the fix's effect on retention not measured yet).

The Studio skill `rbx-instrument-analytics` can place the calls. Read the dashboards weekly (section 3).

## 4. Age, safety and content maturity (check before design is final)

- **Content maturity** is required: without it Roblox restricts playability for everyone. Fill the Maturity & Compliance questionnaire (Creator Dashboard > experience > Publish settings or Audience > Maturity & Compliance); answer for the most mature content a player can meet. Misrepresenting it risks moderation. It also asks whether the game sells paid random items or allows paid item trading, and whether it respects `ArePaidRandomItemsRestricted` and `IsPaidItemTradingAllowed`: answer from what the code does (docs `content-maturity`). A new universe needs its own questionnaire.
- **IARC ratings (docs `content-ratings`, read 2026-11-11):** Roblox is moving to IARC regional ratings (the Australian Classification Board and other authorities). Existing Kids & Select games get IARC ratings pre-filled by reviewers to review and accept (email notice; Creator Dashboard > Publish settings > Content ratings); new eligible games get them after meeting the Kids & Select requirements. A Kids & Select game without assigned IARC ratings by 2027-01-26 may be removed from the Kids & Select catalog in Australia until it is rated. Rating moderation is appealed from the game's Issues & appeals page. The announcement (DevForum t/4985897, 2026-11-10) adds: pre-filled ratings are ready for review no later than the end of December (Creator Dashboard > game > Configure tab), the ACB rating shows only in Australia and only from 2027-01-26, and appeals of an IARC rating open when ratings go public in January 2027; games outside Kids & Select need no action.
- Labels and who can play: **Minimal / Mild** reaches Roblox Kids (5-8) and Select (9-15); **Moderate** reaches Select (9-15) and standard (16+); **Content May Vary** needs age-checked 16+; **Restricted** needs age-verified 18+ (servers run restricted). Realistic or excessive violence, blood, crude humour or romance in uploaded assets can be moderated whatever the label.
- **16+ release path:** account in good standing and at least 2 days old, age check, and answer the first questionnaire question (answering No gives Content May Vary, 16+ only). A maximum of 5 first-time releases per day.
- **Simpler publish flow (since Oct 2026):** Studio File > Publish asks one question; a game with no age-restricted content answers No and reaches players 16+ (Content May Vary) in most regions instead of filling the full questionnaire (up to 30 questions). The full questionnaire is still needed for restricted content or Kids / Select reach. Audience is set in Creator Hub > Manage Audience (Playtest / Public); "Playtest" replaced Private and Limited (details: `roblox-release-automation` section 1). **Early testers:** invite up to 10 friends to preview an unpublished game in the Roblox app. Highly Engaged Player counts in Creator Hub update hourly.
- **Roblox Kids / Select (all ages):** age check plus facial age estimation or ID verification, 2-step verification, Plus/Premium for 2 consecutive months or a 1,000 Robux refundable fee (50,000 for expedited review), the full questionnaire with a Minimal/Mild/Moderate result, and an evaluation of 100 unique plays by highly engaged age-checked users within 60 days (docs revised 2026-11-20, read 2026-11-24; it was 250; games that had already met the threshold are unchanged, per the official weekly recap of 2026-11-20; evaluated hourly, progress under Creator Hub > your game > Publish Settings > Manage Audience). A highly engaged player meets requirements on account tenure, playtime in your game and platform spend: a minimum purchase anywhere on Roblox in the last 60 days, none needed in your game, so a free game counts (docs FAQ; it gives no amounts and says the criteria will change). Until the threshold the game stays with age-checked users 16 and older; ads that speed it up: section 2, sponsored campaign setup. A DevForum post (2026-09-11) gives a maintenance bar of 25 since 2026-07-16 (not in the docs): re-read the docs before quoting. Select-only publishing drops the fee/subscription requirement. Creators who got the free 6-month Roblox Plus grant keep a publishing fee waiver until 2026-12-19; after that, publishing a new Kids & Select game needs the refundable fee or another eligible requirement, and existing games stay live (staff updates 2026-10-30 and 2026-11-12, DevForum t/4567894). Confirm the intended audience in `roblox-project-intake`.
- Free text between players (signs, boards, pet names, trading notes) outside `TextChatService` is enforced against now; see `roblox-engine-2026` section 5.
- Age checks (facial age estimation) gate chat and other features; do not build features that bypass `TextChatService` filtering. Platform-integrated chat becomes mandatory for all games in May 2027 (see `roblox-engine-2026` section 5), and voice chat is limited to experiences of 100 players or fewer. Custom Quick Words (live 2026-10-13): up to 3 categories of 3-10 phrases, each under 25 characters, English input, reviewed; set at Configure > Chat > Quick Words.
- **Generative AI in games:** Roblox-served AI (`GenerationService`, `TextGenerator`) is moderated and aims at All Ages; third-party AI output is your responsibility and must follow Community Standards. A game whose main purpose is continuous chat with an AI character, or whose AI remembers prior sessions, has "extended AI interactions": answer Yes in the questionnaire and expect a Restricted (18+) label. **Required disclosures (docs `generative-AI`):** at the start of any AI interaction and throughout the session, show a visible notice that the player is talking to AI (example: "This is an AI-powered conversation, not human. It may make mistakes."); direct players who seek medical or professional advice to authoritative resources, and when a player shows signs of self-harm or a mental health crisis, the AI must encourage them to seek support and point to crisis resources.
- Disclosures, IP and rights: follow the IP guidelines and Rights Manager; keep `assets/LICENSES.md`; do not publish copied art or music.

## 5. Pricing and balance changes

- Change one thing at a time and measure with an experiment, not a feeling (offline economy sims change price growth and per-tier gain together: section 1, 'Economy sim rules').
- Regional pricing is on by default for Robux subscriptions; plan prices accordingly.
- **Managed Pricing** (regional prices and price tests): new games and items are enrolled by default. Price tests need about 60,000 transactions per 30 days, so most new games cannot use them. It cannot fix prices hard-coded in UI (section 2, Plus row).
- Never raise prices on existing owners of a pass without a clear value add.

## 5b. Discovery (what the recommender rewards)

- Recommended for You retrieves then ranks; ranking counts only users who arrived through it. Strongest signals: play-through rate, first-play bounce rate (negative; 61-180 s window), play days per user (D1, D2-7, D8-28), playtime per user (capped at 60 min per user per game per day). Also: co-play days, qualified sessions, spend days, Robux spent per user. Signals are per-user averages, so small games are not penalised and new games need no 28-day wait.
- A custom thumbnail is required for home recommendations (in force since 2026-10-19: a default thumbnail gets no Home impressions). Metadata that does not match the content, giveaway-led titles and near-duplicate games hurt exposure.
- Description: the first about 160 characters matter most (common guidance, not found in the docs; about 1,000 total); hashtags and tags are not used.
- Promotional Text (beta, 2026-11-03; Creator Hub > Creations > Game > Game details): a short secondary line for a limited-time mode or update, so the game name stays short instead of carrying "[UPDATE]" tags. Roblox tests its placement on a small audience, so where it shows may change. Creator Hub warned that long text may be cut off on some app screens once about 24 characters were typed (field note, 2026-11-09): keep it to one short line and change it with each update.
- Other surfaces: Standout Games, Sponsored, semantic Search, Discover, notifications, experience events (max 10 events; update posts up to 60 characters, once every 3 days).
- Event surfaces (docs `experience-events`): **Trending Events in Experiences** lists a public event that started within 7 days and has 1,000+ RSVPs; **Off-Platform Featuring** (App Store, Google Play) needs the event submitted at least 7 days ahead; events running 7-30 days do best.
- **Moments** (newsroom 2026-07-28): a tab of player clips with a Join button, 16+ age-checked users only, rolling out from Canada, New Zealand and Singapore. Plan one clip-worthy moment (a big reveal, steal or win); in-game recording and share links (`CaptureService`, `SocialService:PromptLinkSharingAsync`) are in `roblox-fun-effects` section 6. Programs worth knowing: Creator Rewards, Developer Awards, Standout Games, Learn & Explore, Jumpstart (18+ novel games), Incubator.

## 6. Publish checklist

Who does what (agent vs user), API key scopes and missing-permission handling: `roblox-release-automation`. Benchmark gates: `roblox-launch-benchmarks`.

1. Dev place tested; a private test place built from the exact publish build; tester told what to check and the known issues.
2. Content maturity done; genre and subgenre chosen (definitions in docs `production/publishing/experience-genres`: a game where each simple repeated action raises a counter is Simulation > Incremental Simulator; Idle is for little to no player input); description honest (include controls, update notes; do not stuff keywords).
3. **Icon** 512x512 (previews scale down to about 150 px; check it small). **Thumbnails** 16:9, 1920x1080, under 3 MB; up to 10 images/videos; uploaded video has a monthly quota (3 uploads); YouTube video links were removed from game pages on 2026-09-30, so upload video files. Craft rules in `roblox-store-art-pack` section 5.
4. Localization: add source text, auto-translate or manual translations; check long strings in the UI (docs `production/localization`; accessibility: `production/publishing/accessibility`).
   - Source strings: a table entry matches a label's whole `Text` exactly and case-sensitively (docs `add-source-content`), so add the static literals players read (labels, names, descriptions, toasts). Automatic Text Capture can take up to a few days (docs); faster is Studio's Automatic Text Capture while playtesting (1-2 minutes, docs) or pushing the sources yourself: `scripts/l10n_sync.py` extracts literals from a Rojo src tree and adds only the missing ones (API in `roblox-release-automation` section 1). Pushed strings were auto-translated into every enabled language within minutes (one game, 2026-11). Runtime-built text: `roblox-ui-typography` section 7.
5. Accessibility (readable text, contrast, never colour or sound alone, honour `GuiService.PreferredTransparency`, `PreferredTextSize` and reduced motion); console (10-foot UI, TV-safe area, full controller navigation, no chat window); VR (OpenXR, default camera scripts, instance streaming, Quest aims for 72 fps); device and network simulator checks.
5b. Localization: source and supported languages, `AutoLocalize`, fonts that cover each language (`roblox-ui-typography` section 7); auto-translate covers 18 languages (Arabic, Chinese simplified/traditional, English, French, German, Hindi, Indonesian, Italian, Japanese, Korean, Polish, Portuguese, Russian, Spanish, Thai, Turkish, Vietnamese; the live list from English also had Dutch on 2026-11-04: `GET https://gameinternationalization.roblox.com/v1/automatic-translation/languages/en/target-languages`, no auth).
   - Source language first: it defaults to the creator account's language (docs), and text is assumed to be in it. A Korean-locale account with English strings got no translations at all (2026-11). Check with no auth: `GET https://gameinternationalization.roblox.com/v1/source-language/games/{universeId}`.
   - Settings (Creator Hub > Audience > Localization; docs `automatic-translations`): per supported language **Experience Strings & Products** on (**Experience Information** for the name and description); Settings tab: text capture from experience UI on and **Use Translated Content** on. Never press **Clear unmodified auto-captured entries**: it deletes those entries and their translations (docs `remove-content`).
   - Which languages: every one the auto-translation quota allows (initial and monthly, per character and per language, shown on the Languages tab). Rank by Creator Hub > Analytics > Demographics (country, top languages) and the target audience, not third-party country shares. Check that the main country of a language does not block Roblox before adding or skipping it: Turkey blocked it from 2024-08-07 until 2026-06-18 (Turkiye Today), and Russia has blocked it since 2025-12-03 (Interfax; talks on lifting it in 2026-06). When the user rejects auto translation, keep it off for the name and description and write them per language (`roblox-release-automation` section 1). Analytics: log events after success, not on attempt; custom events max 100 names; data rolls off after 90 days.
   - Text inside images (beta, staff post 2026-11-09): automatic image translation redraws the text of in-game images in the player's language, for French, German, Indonesian, Italian, Korean, Portuguese and Spanish only; icons and thumbnails are not covered. It is off by default: on the Localization page enable it per language (Languages tab), turn on Automatic Image Capture and Use Translated Content for images (Settings tab). Images are captured as players meet them, so translations can take a few days; review them on the Translate page's Images tab, and set `AutoLocalize` false on an image that must stay as it is. Translated images cannot be uploaded by hand yet (planned for early 2027 per the post). Text kept in a `TextLabel` over the image stays the safer build, since it covers every language (judgment). Not tested by us.
   - Test a locale in Studio with Test > Player Emulator > Enable Test Profile > Locale (docs `studio/testing-modes`). `PlayerEmulatorService` was nil from MCP `execute_luau` (field note, 2026-11-09). What worked for an agent instead:
     - put the exported table CSV in a scratch Rojo project (Rojo builds a `.csv` into a LocalizationTable) under LocalizationService;
     - in Edit, set the table's `SourceLocaleId` to another locale ("fr") and copy the target language's column into the `en` and `en-us` values;
     - keep the original table aside and never ship the scratch project.
6. Assets owned by the publishing account/group and verified loadable in a live client.
6b. Group-gated rewards: the group must let outsiders join without manual approval, or no outside player can claim them. Check `publicEntryAllowed` on `GET /cloud/v2/groups/{id}`; changing it is a group-owner step, so list it in the hand-off.
7. Publish through Open Cloud (`versionType=Published`; `Saved` stages a version without releasing it); record the version number; keep the rollback version. The API skips EditableImage, EditableMesh, PartOperation, SurfaceAppearance and BaseWrap instances, so publish those places from Studio.
8. Day-1 watch: crashes, error reports, funnel drop-off, DataStore errors.

## 7. Account and rights hygiene

- Use a group-owned experience for teams; assets uploaded to the wrong owner render blank. Pick the owner before the first publish. A later move is the Creator Hub game ownership transfer (docs `projects/game-ownership-transfer`):
  - Start: Creations > game > Publish Settings > Game details > **Initiate ownership transfer**; the sender needs publish rights in the group. The group owner accepts (docs). A group admin who started a transfer saw only **Cancel transfer request** and no accept button (field note, 2026-11-09), so book the owner's time.
  - Before: the group must own the game's private ModuleScripts, InsertService assets and packages (docs). List every id the code passes to `InsertService:LoadAsset` first (one game had about 277). An API key keeps the access of the user who last generated it, so a move to a group that user does not own needs new keys (docs).
  - Timing (docs): a request expires after 7 days; a received game cannot move again for 30 days; edits made after acceptance, while the transfer runs, are not carried over.
  - After (docs): ids and URL stay; accepting closes all servers and makes the game private until it is released again; card details are removed; existing private server subscriptions pay the group without revenue splits; search is unaffected if the title stays the same, but discovery can dip for up to 24 hours after the re-release. The page says nothing about passes, products, asset permissions or the questionnaire, so read each back after a move. One game that moved by recreating it on a new universe had to redo all of them (2026-11).
  - After a move (field note, 2026-11-09): re-upload images and models under the group (Assets API `creationContext.creator.groupId`), then check every id with `GET /assets/v1/assets/{id}?readMask=moderationResult,creationContext` before publishing. In that game all 276 ids came back Approved and group-owned.
- Turn on 2-step verification; use API keys restricted to the one experience with the minimum scopes; keep keys in env files. IP allow-lists break keys used from Roblox servers, expiry dates need a rotation process, and keys unused for 60 days expire. Asset scopes follow the creator (user or group), so a user key cannot manage group assets without the group role.
- Create the game and its dev place separately; never edit the live place in Studio.
